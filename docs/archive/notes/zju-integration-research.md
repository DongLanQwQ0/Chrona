## 实际只读验证补充

用户授权后已验证登录成功，查询课程列表及当前学期十门课程的活动与作业提交状态。只保存/输出字段结构与计数，不保存会话和原始响应。

- 课程列表返回 14 门，分页元数据 pages=1、total=14；其中 10 门属于接口标识的当前学期。本次课程列表已覆盖该查询的全部页。
- 十门课程活动中共观察到 21 个 homework 条目；均含 `updated_at`，本次样本的 `deadline` 与 `end_time` 相等，时间为带时区 ISO 格式。可以保存服务端更新时间，但仍需验证它是否覆盖所有教师变更；样本相等不代表两个截止字段永远相同。
- 五门课程提交状态接口成功，另五门返回 HTTP 404；这五门的活动列表没有 homework。不能在一般规则中把 404 当成空列表，更不能当成已完成或被删除。
- 本账号的 `classroom_schedule` 非空值是自由文本字符串，其他部分为空字符串或 null；非空样本不含周次/节次标记。该字段不能据此实现完整结构化课表；后续已从教务系统菜单找到实际课表入口，见下节。
- 提交状态列表与活动列表条目数存在差异，不能按数组位置匹配或因活动列表缺项而删除；必须按稳定 id 关联并继续调查覆盖范围。

验证脚本位于构建目录，不含凭据。会话仅存在于进程内，进程退出后未持久化。原调研文档备份于 `build/backups/zju-research-before-live-verification/`。

开发后的原生只读验证：正式 Java ZjuClient + OkHttp 取得 10 门当前学期课程、21 项作业和 277 节秋冬课程；11 项提交状态确定为已提交，10 项未知保留 null。该验证未展示学号、密码、Cookie 或私人正文。

## 1. 结论：作业走学在浙大，课表走教务系统

作业已有结构化接口，可以直接读取作业标识、标题、截止时间和提交状态，无需 AI。课表通过本地依赖提供的教务登录流程，进入学校真实页面并追踪该页面脚本，已成功获取排课响应；不使用学在浙大的自由文本字段充当完整课表。

推荐先完成统一来源管理和作业增量同步，再接入课表解析与日期展开。课表接口已定位，教学周历、调课及非固定时间课程仍需验证。两者共用来源与提醒规则，但互不阻塞。

### 教务课表只读验证

通过 `login-zju` 的 ZDBK 登录后，从首页脚本发现菜单查询接口，再由菜单返回真实的“学生课表查询”页面；没有枚举猜测接口。

来源链（主机 `https://zdbk.zju.edu.cn`）：

1. `/jwglxt/xtgl/index_initMenu.html` 首页及所引用脚本。
2. `/jwglxt/xtgl/index_cxFilterGnmkdm.html`，POST `gnmkmc=课表`，返回菜单地址和功能代码。
3. `/jwglxt/kbcx/xskbcx_cxXskbcxIndex.html`，使用菜单返回的功能代码；页面提供学年、学期选项。
4. 页面引用 `/jwglxt/js/comp/jwglxt/xkgl/kbcx/xskbcx.js`，给出真实查询参数与响应消费方式。
5. `/jwglxt/kbcx/xskbcx_cxXsKb.html`，POST `xnm,xqm,xqmmc,xxqf,xsfs`，附该功能代码。

本次按页面选项查询 2026-2027 秋学期：

- `xxqf=0,xsfs=0` 网格模式返回 20 条 `kbList`，并有 3 条 `sjkList`、`kbcdList` 等分组。20 条是排课记录数量，不能称为 20 门课程或 20 次实际课程。
- 网格记录含 `xkkh`、`jszgh`、`djj`、`dsz`、`skcd`、`xqj`、`xxq`、`kcb`。前端用 `djj` 定位节次、`skcd` 作为跨行长度、`xqj` 定位星期；`dsz=2` 跨两列，其他编码还需结合表头确认，不能凭名称猜单双周含义。
- `kcb` 是含 `<br>` 的展示片段，含标题、日期提示和地点等内容，不能作为可靠的跨来源主键。需按学校格式解析，不执行返回 HTML。
- `xsfs=1` 列表模式返回 14 条课程记录，含 `kcdm,kcmc,xkkh,jszgh,jsxm,xksj,xxq` 等。本样本的 `xksj` 是时间戳格式字符串，未提供可直接替代完整排课的 `sksj/skdd` 字段。列表与网格用途不同，不能互相覆盖。
- 学校前端给出 13 节作息：08:00–08:45、08:50–09:35、10:00–10:45、10:50–11:35、11:40–12:25、13:25–14:10、14:15–15:00、15:05–15:50、16:15–17:00、17:05–17:50、18:50–19:35、19:40–20:25、20:30–21:15。该证据来自当前教务脚本，适用校区与未来变动仍需核对。

下一步应将列表的课程身份与网格排课关联，验证日期提示、单双周、短学期、实践课程、教学周历与节假日调课。没有实际时间的实践课程保留为未定时间，不制造日历提醒。

## 2. 本地代码提供了什么

### 作业

`courses.zju/reliableTodolist.js` 使用以下接口，主机为 `https://courses.zju.edu.cn`：

| 接口 | 已使用的数据 |
| --- | --- |
| `/api/my-semesters` | 学期 id、名称、是否当前学期 |
| `/api/my-courses` | 课程 id、名称、课程代码 |
| `/api/courses/{courseId}/activities` | 活动 id、标题、类型、发布状态、开始与结束时间 |
| `/api/course/{courseId}/homework/submission-status?no-intercept=true` | 作业 id、status_code；代码识别 submitted |
| `/api/courses/{courseId}/exams` | 考试条目 |
| `/api/courses/{courseId}/submitted-exams?no-intercept=true` | 已提交考试 id |

可生成作业原页面链接：`/course/{courseId}/learning-activity#/{activityId}`。

原脚本是“展示当前未完成事项”的工具，不能直接作为同步器复用：

- 会排除逾期、尚未开始、无截止时间、已提交的条目，无法保存完整历史。
- 部分请求失败会变成空数组；空数组不代表作业被删除。
- 课程查询仅第一页、大页容量；尚无完整分页证据。
- 通过当前学期 id 加一、加二猜测相邻短学期，不能用于可靠学期发现。
- 没有使用教师修改版本或更新时间，不能声称掌握真实修改时间。

### 登录

本地依赖 `login-zju` 1.0.9 的源码映射包含统一认证和学在浙大登录流程：获取 CAS 页面 execution、获取 RSA 公钥、提交加密密码、跟随服务重定向并保存 Cookie。

这证明协议路径有参考实现；尚未证明验证码、多因素认证、会话过期重登及校外网络均可用。遇到认证挑战时停止自动重试并提示重新登录，不尝试绕过验证。

### 课表

`shared/choose-a-course.js` 请求 `/api/my-courses`，字段包括 `academic_year_id`、`semester_id`、`start_date`、`end_date`、`course_attributes`、`classroom_schedule`、`imported_from`，但仅消费课程 id 和名称。

`zdbk.zju/gradeMonitor.js` 是成绩查询；`classroom.zju/generateCourseMd.js` 是录播目录。它们都不能证明完整课表读取能力。录播条目的开始时间不能直接当作教学课表。

## 3. 设置结构

设置新增「浙大服务」，默认关闭：

- 启用浙大服务；账号、密码；登录状态；立即同步；最近成功时间。
- 同步作业与提醒：独立开关。
- 使用浙大课表：独立开关，接口验证后提供。

设置新增「日程来源」：

- 导入的课表：按导入课表/学期启用。
- 系统日历：按系统日历启用，显示账号与日历名用于区分。
- 浙大课表：按账号与学期启用。
- 同一学期选择一个课表主来源；其他来源保留数据，仅抑制已确认重复的课程显示和提醒。

原位置的“包含系统其他日程”等开关保留。实际可见性为：全局来源允许，并且当前页面允许包含系统日程。通知还需满足通知设置，不把“页面隐藏”和“关闭通知”混为一个状态。

## 4. 一个「作业」capture，稳定更新每项作业

以受管理的内部标识识别 capture，显示名称固定为「作业」；不根据名称搜寻或占用用户自己创建的同名收件。

作业身份使用平台、账号命名空间、课程 id、条目类型、条目 id 的组合。标题和截止日期属于可变字段，不参与身份判断。该组合仍需真实响应确认其稳定性。

同步采用逐项新增/更新，保留候选项 id、完成状态和日历链接；禁止使用清空再重建的 replaceCandidates。

每项保留：来源标识、上次成功观测值、本地修改、最近观测时间、同步状态及变更历史。历史记录修改前后值和“同步发现时间”；接口没有教师修改时间时不编造它。

### 建议的更新规则

| 情况 | 行为 |
| --- | --- |
| 新发布作业 | 新增待办，提醒一次 |
| 教师修改标题或截止时间 | 更新来源字段、记录历史、撤销旧提醒并重新安排；变更提醒一次 |
| 无截止时间 | 保留为待安排，不推测日期 |
| 逾期未交 | 保留为逾期待办 |
| 已提交 | 建议自动完成来源管理的作业，保留提交历史 |
| 用户已手动完成 | 后续普通内容修改不重置为未完成 |
| 用户安排执行时间或提前提醒 | 与官方截止时间分别保存，更新截止时间不覆盖个人安排 |
| 请求失败、分页不完整、某次未返回 | 保留旧数据，不推断删除或完成 |
| 服务器明确撤回/删除 | 保留历史，停止提醒；具体状态字段待响应验证 |

提交状态与本地完成状态分别记录；撤回提交、重新开放作业是否重开待办，需要在实际状态契约确认后确定。

首版建议仅把作业类活动转为作业待办。考试与课堂活动不因出现在同一接口就自动归入作业。

## 5. 删除与关闭必须阻止重新生成

- 关闭作业开关：停止同步及该来源后续提醒，保留历史和已有待办。
- 删除整个「作业」capture：同时关闭作业功能、解除绑定并增加同步代次。已在途请求返回后必须检查代次和绑定，不得重新创建 capture。
- 删除单项作业：记录该远端条目的忽略标记，普通同步不得重新导入。
- 再次开启：由用户明确恢复同步；不能由后台工作或云同步隐式开启。

这些规则必须放在统一删除入口，覆盖详情页、批量删除、局域网页面及同步删除，不能只改一个按钮。涉及系统日历删除失败时先停同步，再保留可恢复数据并报告失败。

## 6. 全局来源过滤与去重

系统日程读取汇聚在 `CalendarStore.listInstances` 和 `reminderInstances`。查询结果需携带 calendar id、账号及日历元数据，并在数量限制之前应用来源规则。

必须覆盖首页、日历、周图片导出、小组件、原子通知/普通提醒、局域网页面，以及旧入口打开详情时的可见性检查。日历链接维护、实际删除和恢复检查不使用展示过滤，避免把“隐藏”误判为“已删除”。

现有导入课表虽然有 `CourseAgenda.load` 展开能力，但尚未接入所有共享消费入口；需要补齐真实的数据通路，而不只是增加来源选项。

去重分两层：

1. 来源内部用稳定 id 和发生实例标识更新；ICS 优先保留 UID 与 RECURRENCE-ID。
2. 来源之间有强标识或用户确认映射时，按主来源抑制重复；仅标题、时间、地点相近时提供建议，不自动删除。

系统日历名称只能辅助识别，不能可靠判断由哪个应用写入。混合日历中的普通日程不能因为含有课程就整本隐藏。导入和 API 课表默认作为只读来源展示，不自动再次写入系统日历，避免循环重复。

## 7. 后台、隐私与数据规模

- 后台定期拉取建议约 30 分钟，结合手动同步和打开应用后过期刷新；Android 后台调度无法承诺精确轮询时刻。
- 作业截止提醒复用现有本地提醒管道，不依赖应用前台。
- 网络请求在数据库事务外执行；提交时再次检查账号、启用代次和 capture 绑定。
- 密码和 Cookie 使用独立 Android Keystore 加密存储，不进入 AI、日志、局域网导出或普通云备份；退出账号清除会话。
- 本地参考项目主包为 GPL-3.0-only，登录依赖为 MIT。实现时记录来源与许可，不能把整段复制当作无条件可复用代码。

调研时 `TaskCodec` 每个 capture 限制 2000 项，现已明确提升为 30000 项和 16 MiB 校验，超限报告错误，不截断或拆成多个收件。作业的远端映射、历史和本机忽略标记在独立DB表，完整备份包含这些表；WebDAV仍同步普通capture结果、以整个capture为冲突单位。学校账号不云同步，建议一台设备负责拉取，多设备并发修改仍沿用现有冲突确认流程。

## 8. 未解决项与取证条件

### 必须验证的接口事实

1. 本科教务课表入口和本账号响应已验证；仍需验证研究生覆盖、日期展开、单双周、停课、调课、补课、考试及学期边界。
2. `classroom_schedule` 本账号样本为自由文本或空值，完整课表采用教务接口；校历、不同校区作息、实践课无固定时间的语义待核对。
3. 作业分页、稳定 id、时区、无截止时间、延期、撤回、补交、团队提交与重新提交状态。
4. 会话过期、验证码/多因素认证及校外访问条件。

用户已授权通过本地账号文件进行只读登录；后续取证继续使用脚本引用，不读取、回显凭据，不在聊天中接收密码。接口发现沿学校页面及其脚本继续，不枚举未知接口。

### 已采用的产品规则

- 学校显示“已提交”时自动完成对应作业；本地手动完成不因普通更新而撤销。
- 用户单独删除作业后保持忽略；本版没有单项忽略列表恢复入口。
- 明确重新开启已删除的「作业」capture 后，重新导入已发布作业并按已提交状态完成；已完成项不触发新增作业提醒，原变更历史保留。
- 同一账号建议只由一台设备拉取学校数据，其他设备接收普通同步结果；凭据不随云同步分发，本版没有自动主设备选举。

## 9. 实施顺序与完成条件

1. 定义来源、外部身份、作业历史和逐项同步契约，覆盖备份及删除代次。
2. 完成来源设置及全部消费入口过滤，接通已有 ICS 来源。
3. 接入认证与作业读取，验证增量更新、截止变更、失败保留、删除不复活及后台提醒。
4. 基于已验证的教务响应补齐课表日期与作息规则，再接入浙大课表，验证主来源切换和跨来源重复抑制。
5. 开发集中完成后做少量完整回归；真机可用时再确认后台调度与原子通知实际表现。

完成以真实数据和状态变化为准：重复同步不增项、修改截止只更新原项、失败不清空、删除不复活、来源过滤在所有入口一致、生效提醒不依赖应用前台。
